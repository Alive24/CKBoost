Creation extension compatibility

The new organizer routes follow the updated Figma role decision. A current on-chain Endorser whitelist entry grants Organizer creation. Editing and staff assignment require that grant plus ownership verified from this exact campaign cell's configured type/lock scripts and ConnectedTypeID arguments. Admin override remains. A reviewer can review assigned submissions without acquiring creation/editing rights. Entry and transaction authority comes from fresh chain reads, never optimistic ProtocolProvider role state. Original page UI is unchanged.

The routes use CampaignAdminService and verified Nostr publishing. Quest IDs, accepted-user IDs, counters, status and token/NFT assets come from the current chain cell on edits. An unused published quest can be removed without renumbering other IDs. Actual pending/accepted submissions or completion/reward history block deletion with a specific reason; unavailable submission history blocks deletion until it is verified. Configured rewards alone do not prohibit deleting an unused quest. Deletions and required-response changes are checked again before and after relay work.

Quest content stays `ckboost-campaign-quest-content`, version 1. An optional boolean `required_response` is added only to the Nostr subtask payload, never the chain codec. New subtasks default to required; undefined retains the legacy policy. Both setup title/instructions remain required independently. Rich quest descriptions and evidence requirements survive drafts/templates separately from chain state.

The named IANA zone is stored in a capped, versioned HTML comment on the Nostr long description: `<!--ckboost-campaign-settings:v1:<URI-encoded JSON>-->`. Decoding validates the zone with Intl and strips the comment from editor/display content. Unix seconds remain authoritative. Loaded schedule seconds and DST folds round-trip unchanged; newly typed nonexistent or ambiguous clocks reject. Legacy editors can strip the optional comment when rewriting descriptions; timestamps remain correct but the original named zone may be unavailable.

Drafts, templates and resumable transaction receipts are local to the device and scoped to network, full protocol hash and connected signer lock hash. Resume and replacement are explicit. Empty rules and zero verification requirements replace previous template values. The present creation frames configure points only; exporting templates containing CKB/UDT/NFT rewards is explicitly blocked rather than silently dropping reward definitions or funding a new campaign implicitly. Existing reward-bearing campaigns remain editable with assets preserved. The separate reward/quota/funding concept is outside these creation frames.

The publishing dock follows actual Nostr verification, wallet/send results and the shared finalized transaction tracker. It never simulates success. Link navigation/full unload offer exit confirmation. Browser Back/Forward uses noncancelable popstate after traversal; Next also restores its internal tree from that event. A local handler flushes the latest authorized draft without rewinding or injecting history, and unmount flush is tested. The custom Save/Discard/Keep editing modal does not intercept App Router browser traversal; a router-wide navigation guard is needed for that parity.

Entry authority checks and existing-submission scans each have a 12-second UI deadline with their own Retry action. Expired or old signer/client/route scopes cannot update UI. Checks stop before follow-up campaign queries, and read-only scan iterators stop requesting further pages after expiry. The scan service is constructed directly from the successful fresh authority snapshot; it does not wait on a second global ProtocolProvider request or CampaignAdminProvider. The same service builder supplies the publishing adapter.

Full description retains the legacy requirement: the original editor rejects an empty description without an existing Nostr reference, and the campaign-type validator requires nonempty metadata.long_description. Markdown is supported by the shared sanitized renderer. Visible difficulty names are Easy / Intermediate / Hard; numeric codes remain 1 / 2 / 3.

Deployment capability for Organizer edits

`NEXT_PUBLIC_CKBOOST_ORGANIZER_AUTH_LOCK_HASHES` is an explicit comma/whitespace-separated allowlist of full `0x` + 64 hexadecimal-character protocol-lock code hashes. It defaults empty. Malformed entries fail closed. Do not configure placeholder hashes. The non-admin edit path compares the actual input campaign lock.codeHash after role/ownership validation, and repeats this before signing. The editor remains enabled for an authorized Organizer; publishing on an unsupported deployment reports that access is confirmed but the protocol authorization upgrade is required. Admin's existing path is unaffected, including an empty/malformed allowlist.

Populate the allowlist only after an operator verifies the upgraded protocol-lock deployment and records its confirmed on-chain outpoint/data hash, checks its script code hash against the protocol configuration and actual input campaign lock, and validates the Organizer-owner and reviewer separation tests. A Type ID script hash is not the bytecode data hash; an in-place code upgrade can keep the same script hash, so the hash alone is not evidence of an upgraded binary. Source fixes and local tests do not upgrade a deployed contract. No value is automatically populated and no deployment/signature is performed by this code.
